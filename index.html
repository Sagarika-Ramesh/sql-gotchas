SQL Gotchas, Illustrated

Window functions

LEAD counts rows, not days

LEAD(column, n) returns the value from n rows ahead. It doesn't look at the dates. If every day has exactly one row, n rows and n days are the same thing. Once weekends, holidays or missing data leave gaps, they aren't.

To get the value exactly 7 calendar days later, join the table to itself on the date difference. Use a LEFT JOIN, so a day with no partner comes back as NULL and doesn't vanish.

👉

Want to keep using LEAD? Fill the gaps first. Join to a generate_series calendar so every day has a row, and then LEAD(amount, 7) really does mean 7 days.

Joins

Self-joins: one table, two aliases

A self-join compares rows within one table. You give the table two aliases and treat them as two copies, for example e1 as "the employee" and e2 as "the manager". The ON clause defines how a row in one copy relates to a row in the other.

Who reports to whom (and org charts)

Look up each employee's manager in the same table. The LEFT JOIN keeps the person at the top, who has no manager.

Each self-join climbs one level of the hierarchy. For a chain of any depth, use WITH RECURSIVE.

Top item within a group

Joining p1.price < p2.price within a category lists every "cheaper than" pair. That's the comparison, but not yet the answer. To get the most expensive product per category, keep the products that have no pricier partner.

Pairs that share something

To find students enrolled in the same course, compare the IDs with < rather than <>. With <> you get every pair twice, as (A, B) and again as (B, A).

Gap between consecutive rows

The self-join l2.log_id = l1.log_id + 1 assumes the IDs have no gaps. Deleted or rolled-back rows break that assumption. LAG uses the actual order of the rows and is simpler to read.

Rolling windows by date

For a 7-day moving average, match each day with itself and the 6 days before it. In my original note the range pointed forward in time, so this version flips it.

Duplicate rows

The condition signup_date <> signup_date misses duplicates that signed up on the same day, and it reports every pair twice. Compare a unique key instead. If you only need to know which emails are duplicated, GROUP BY is simpler.

The mental model

The order SQL actually runs in

You write SELECT first, but the database evaluates it near the end. Many of the traps below have the same cause: a clause can only see what ran before it.

👉

This is the logical order. The query planner can reorder the physical work, but the result always has to match this order. Keep it in mind and you won't have to memorize the WHERE/HAVING, alias and window-function rules below.

Where rows go missing

Join traps

J1INNER JOIN drops what didn't match

Ask
List all products and their total sales, including products with zero sales.
Trap
INNER JOIN keeps only products that have sales, so the zero-sales products disappear.

J2A WHERE filter quietly turns a LEFT JOIN into an INNER JOIN

This is the most common one. Unmatched rows come out of a LEFT JOIN with NULL in every right-table column. A WHERE condition on one of those columns evaluates to unknown for those rows, so they get dropped.

The same idea with aggregates: count each employee's Q3 queries and include employees who ran none.

👉

MAX needs COALESCE because it returns NULL when an employee has no matching rows. COUNT(column) already returns 0 for that case, so it doesn't need it. Filters on the left table still belong in WHERE. The rule applies only to the right side.

J3"Never did X" needs an anti-join

Ask
Find customers who have never placed an order.
Trap
A plain JOIN returns only customers who do have orders. You need to keep the unmatched rows and then select those.

J4Join conditions hiding in WHERE

With comma joins (FROM orders, customers WHERE ...), the join logic sits among the filters. Forget one condition when you add a third table and you get a Cartesian product. Explicit JOIN ... ON keeps each relationship next to the table it belongs to.

J5SELECT * and join fan-out

Ask
Names of customers who placed an order.
Trap
SELECT * pulls every column from both tables, and same-named columns become ambiguous. The bigger problem is fan-out: a customer with 12 orders comes back 12 times.
GROUP BY, HAVING, OVER

Aggregates & windows

A1WHERE can't filter on an aggregate

WHERE runs before GROUP BY, so SUM(...) doesn't exist yet at that point. Use HAVING to filter groups.

A2Grouping by one column too many

For "total sales per product", adding sale_date to GROUP BY gives you one row per product per day. Group by exactly the grain the question asks for, and aggregate everything else.

A3Filtering on a SELECT alias

Aliases are created in SELECT, which runs after WHERE. Postgres, MySQL and SQL Server reject the query below. Repeat the expression, or compute it in a CTE first. HAVING is the wrong tool here because nothing is being aggregated.

A4Filtering on a window function

Ask
The latest purchase per customer.
Trap
WHERE rn = 1 in the same query fails, because window functions run after WHERE.
👉

Snowflake, BigQuery and DuckDB support QUALIFY rn = 1, which filters on a window result without the CTE.

A5Top N per group: pick your tie rule

A correlated subquery for "top 3 products per category" is slow and hard to read. Rank inside a CTE instead. Choose the ranking function on purpose: ROW_NUMBER breaks ties arbitrarily, RANK keeps ties and skips numbers after them, and DENSE_RANK keeps ties without skipping.

A6LIMIT without ORDER BY

A table has no inherent order. "Top 5" with LIMIT 5 and no ORDER BY gives you 5 arbitrary rows, and they can change between runs.

A7Running totals: use a window, not a subquery

Window functions compute across rows without collapsing them. That makes them a good fit for running totals, rankings and comparisons with a group average.

👉

Without an explicit frame, the default is RANGE. Two orders on the same date then both get the total including each other. Write ROWS when you want a strict row-by-row running total.

A8Correlated subqueries and nesting

Ask
Employees paid more than their department's average.
Trap
A correlated subquery in WHERE can re-run the average once per employee, and nested subqueries quickly become unreadable.

The same CTE-first approach handles "the customer with the highest total in each region". Aggregate in one CTE, rank in a second, and filter at the end. Each step can be checked on its own.

Three-valued logic

NULL isn't a value, it's "unknown"

Any comparison with NULL returns UNKNOWN, not TRUE or FALSE. WHERE keeps only rows where the condition is TRUE, so rows with NULLs drop out without any warning.

N1!= silently excludes NULLs

Ask
Employees whose manager isn't 123, including employees with no manager.

N2NOT IN with a NULL returns nothing

If the subquery returns even one NULL, x NOT IN (...) is never TRUE for any row, and you get an empty result. NOT EXISTS doesn't have this problem.

N3Aggregates skip NULLs

AVG, SUM, MAX and COUNT(column) all ignore NULLs, while COUNT(*) counts every row. If "no rating" should count as zero, say so explicitly. Treating missing as zero changes what the number means, so make that choice on purpose.

Matching

Strings, dates & types

S1Case sensitivity depends on the database

Postgres compares strings case-sensitively, while MySQL's default collations don't. If you need a case-insensitive match, normalize both sides of the comparison.

S2= doesn't understand wildcards

name = 'John%' looks for a name that is literally "John%". Wildcards only work with LIKE: % matches any run of characters and _ matches exactly one.

S3Implicit type conversion

If order_amount is stored as text, order_amount > 100 may compare it as a string (so '9' > '100') or fail, depending on the database. Cast explicitly. Better still, fix the column type.

S4Timestamps aren't dates, and BETWEEN includes both ends

order_date = '2024-01-01' on a timestamp column matches only midnight exactly. BETWEEN '2024-01-01' AND '2024-01-31' includes both ends, but on a timestamp the end is midnight on Jan 31, so almost the whole last day is left out. Use a half-open range: start inclusive, end exclusive.

👉

WHERE DATE(order_date) = '2024-01-01' gives the right answer, but wrapping the column in a function stops the database from using an index on it (see P2). The range version gives the same result and can use the index.

IN, EXISTS, OR

Subqueries

Q1= with a subquery that returns many rows

= expects a single value. The query works today with one active department and fails once there are two. If more than one row is possible, use IN.

Q2Long OR chains

state = 'CA' OR state = 'NY' OR ... is hard to read, and it's easy to get wrong once you mix in AND without parentheses. IN says the same thing in one place.

Q3IN vs EXISTS

Use IN to compare against a list of values, and EXISTS to ask whether a related row exists. EXISTS can stop at the first match. Modern planners usually rewrite both into the same semi-join, so the speed difference is often small. The difference that matters is NOT IN vs NOT EXISTS when NULLs are involved (see N2).

Make it fast

Performance

P1Index what you filter and join on

Columns that appear in WHERE, JOIN ... ON and ORDER BY on large tables are good candidates for an index. If "orders for product X" runs constantly, index product_id.

P2Non-sargable conditions block the index

A condition is sargable (Search ARGument ABLE) if the database can answer it with an index seek. Wrapping the column in a function or arithmetic, or starting a LIKE pattern with a wildcard, forces it to check every row.

P3DISTINCT as a band-aid

Unexpected duplicates almost always come from a join fanning out: one customer, many orders. Adding DISTINCT hides the symptom and makes the database sort or hash every row. Fix the join instead. When the question really asks for unique values, as in "which products have at least one sale", DISTINCT is the right tool.

Likewise, use GROUP BY when you need counts. To count orders per city, GROUP BY city with COUNT(*) does it in one pass.

Interview mode

Before you write a line

Many wrong answers come from misreading the question, not from bad SQL. Spend 30 seconds on these before you start typing.

  • Pin down the grain. Is the output one row per customer, per order, or per day? That decides GROUP BY.
  • Clarify "never" and "all". Does "customers who never purchased" mean ever, or in a given period? Does "all products" include ones with zero sales? These questions decide between INNER and LEFT joins.
  • Ask about ties. For "top 3" with a tie for third place, do you want 3 rows or 4? That decides ROW_NUMBER vs RANK.
  • Test the edges in your head: empty tables, a single row, NULLs, duplicates, and every value the same.
  • Check the order. If the output order matters, write ORDER BY.
Small but handy

Postgres pocket tools

SPLIT_PART(string, delimiter, field)

Splits a string on a delimiter and returns one piece. field starts at 1. Since Postgres 14, a negative field counts from the end.

array_length(array, dimension)

Returns the length of an array along a given dimension. Watch out: an empty array returns NULL, not 0. Use cardinality() if you want 0.
